# Provider feature catalogue

Every endpoint the audit found, per provider, with whether it is usable on an OSM basemap.

**`Basemap?` = yes means the provider's terms require THEIR map be displayed** - which this app
cannot do, because OsmAnd renders OSM. That column kills more features than price does.


## TomTom Maps APIs (developer.tomtom.com / api.tomtom.com)

TomTom is the best-fit traffic provider for CairoDrive's architecture, and the reason is a ToS accident in your favour: TomTom has no "you must display our basemap" clause. Its Map Display docs explicitly state overlay tiles may be layered over "other TomTom or third party map tiles", and the traffic raster tiles are transparent PNGs designed for exactly that. The only binding obligation is attribution. Combined with a free tier that is generous in precisely the bucket a map overlay consumes (50,000 tile requests/day, no credit card), TomTom is the one provider on your list whose traffic layer can sit on an offline OSM basemap without a lawyer. Cairo coverage is real, not aspirational — TomTom publishes a Cairo city page in its Traffic Index (2025 edition: 21.1 km/h average speed, 74 hours lost per driver in rush hour), and that index is derived from the same floating-car-data that feeds Traffic Flow, so probe density in Cairo is deep enough to compute city-wide statistics. Where TomTom is weak for you is everything that is not traffic: Search/Geocoding is strictly redundant with the Google Places integration you already have quota-capped and field-masked; Map Display tiles are pointless against an offline .obf basemap; EV is irrelevant in Egypt; Matrix Routing is a fleet tool; and "Junctions View" is not a public REST API at all. The genuinely under-exploited items are flowSegmentData and incidentDetails for route annotation, the Routing API's supportingPoints reassessment mode, and Snap to Roads as an offline log-audit tool that returns speed limits. Two hard cautions: TomTom revised developer pricing effective July 2026 (a month before today) and I could not read the new page, so treat every number below as pre-revision; and TomTom explicitly warns against mixing Orbis and legacy endpoints in one app.

**Only this provider gives you:**

- No basemap-display requirement — the single most important finding. TomTom's Map Display docs state overlay tiles may be layered with 'other TomTom or third party map tiles', and traffic tiles are transparent by design for compositing. This is the killer clause that disqualifies most providers for an offline-OSM-basemap app, and TomTom does not have it. Attribution is the only obligation.
- A free tier shaped correctly for a map overlay: 50,000 TILE requests/day is a separate bucket from the 2,500 non-tile requests/day. Nobody else splits it this way. Your traffic overlay draws from a pool you will never exhaust, while the scarce 2,500 is reserved for the JSON calls that actually drive logic.
- No credit card required on Freemium, and commercial use permitted. For a personal Play-internal-testing build with no revenue, this removes the 'free tier is a trap' failure mode where a runaway loop generates a bill.
- Demonstrable Cairo probe density, published by TomTom itself: a dedicated Cairo Traffic Index city page with 2025 figures (21.1 km/h average speed, 74 hours lost in rush hour, up 3h50m year over year). That index is computed from the same floating-car data that feeds Traffic Flow, so this is direct evidence of real Egypt coverage rather than a marketing coverage map.
- flowSegmentData exposes `confidence` and `roadClosure` per segment. Confidence is a provider admitting how much probe data backs each answer — it lets you gate ETA correction on data quality per street rather than trusting the whole city equally, which matters enormously in Cairo where arterials and alleys will differ by an order of magnitude.
- Snap to Roads returns speed limits and functional road class per matched segment from a raw GPS trace. That is an independent ground truth against your .obf for one transaction per drive, and it is the only route to authoritative maxspeed data that does not depend on an OSM tag existing.
- Routing API supportingPoints/encodedPolyline reassessment: submit YOUR offline route geometry and get a traffic-aware travel time for exactly that path. Annotation without ceding routing — one transaction, no risk of two engines disagreeing about the roads.
- Plain REST with a `key=` query parameter or a `TomTom-Api-Key` header. No OAuth token exchange, no SDK, no client library, JSON responses. Every endpoint here is reachable from a bare HttpURLConnection, which matters because HERE requires an OAuth flow for parts of its platform.
- incidentDetails has a `fields` selector and a traffic-model-ID (`t`) for change detection — genuinely useful bandwidth controls for a metered-connection data saver, rather than an all-or-nothing payload.

**ToS warnings:**

- Attribution is mandatory and you are probably already in breach. TomTom's terms: for services that auto-generate a logo or copyright notice you must not remove or obscure it; for ALL OTHER services you must implement the TomTom Copyrights API to generate the applicable copyright and logo attribution. Traffic raster tiles carry no embedded branding — they are transparent overlays — so a traffic overlay rendered on your OSM basemap with no '© TomTom' credit is exactly the case that clause covers. Fix this in the map UI before adding any further TomTom feature; it is the cheapest compliance item on the list.
- Do not mix Orbis and legacy endpoints in the same app. TomTom states this explicitly and it is not boilerplate — the two run on different underlying databases and data models, geometries may not align, and feature identifiers are not shared between platforms. For CairoDrive this means committing to one family across traffic tiles, flowSegmentData and incidentDetails together. Orbis is the forward-looking choice (six APIs are GA: Map Display, Traffic, Routing, Places Search, Geocoding, Reverse Geocoding) but the first GA wave is car-and-consumer scope only, and Orbis Routing v2 drops sectionType=lanes, roadShields, tollRoads and handsFreeDriving and restricts travelMode to car. If lane data ever matters you are on legacy — decide now, because switching later re-does every endpoint.
- The SDK restriction does not bind you, but know it exists: TomTom's terms say the SDKs and related materials may only be used in connection with the TomTom Maps APIs. That clause targets the SDKs, not the REST endpoints, and CairoDrive calls REST directly from HttpURLConnection — so it does not apply. But I could not read the full terms document (egress-blocked), so this is a reading of a quoted excerpt, not of the whole agreement. Read developer.tomtom.com/terms-and-conditions in full before shipping.
- Safety-related traffic information (SRTI) has its own separate licence agreement, distinct from the general Maps API terms. If you ever surface hazard-class incidents (ice, fog, dangerous conditions, wrong-way driver) as driver warnings rather than as map decoration, check whether that pulls you under the SRTI terms.
- Play Data safety applies. Every TomTom call sends the user's coordinates to a third party — flowSegmentData sends a point, incidentDetails sends a bbox around where they are driving. That is the same 'Location — precise' disclosure you already made for Places search, so the declaration likely needs no change, but it does need re-confirming rather than assuming, and it applies on internal testing too.
- Matrix Routing bills failed cells: MAP_MATCHING_FAILURE and NO_ROUTE_FOUND matrix cells are charged. Irrelevant if you skip Matrix as recommended, but it is the kind of clause that turns a debugging session into a bill.

## Google Maps Platform

Google is, by a wide margin, the best *data* provider for Cairo — its Places corpus and its crowd-sourced traffic are the only ones with genuinely dense Egyptian coverage — and it is simultaneously the worst *legal* fit for CairoDrive of any provider you will evaluate. The reason is one clause, ToS 3.2.3(e) "No Use With Non-Google Maps" (the clause your brief called 10.5.d; Google renumbered it), which reads: "Customer will not use the Google Maps Core Services with or near a non-Google Map in a Customer Application. For example, Customer will not (i) display or use Places content on a non-Google Map...". Note "with or near" — it is not a display-our-basemap requirement, it is a prohibition on co-presence, and the named example is exactly what CairoDrive ships today. I verified this clause directly from cloud.google.com, and I verified that every single Core Service you asked about repeats it in its own Service Specific Terms section: Places (14.2), Routes (19.2), Roads (17.2), Geocoding (6.2), Route Optimization (18.2), Directions (4.2), Distance Matrix (5.2). There is exactly one sanctioned escape and it is worth the whole report: **Places UI Kit**, whose ToS 15.1 says "Customer may use Places UI Kit in Customer Applications with or without any map, including a non-Google Map. This clause will prevail over the No Use with Non-Google Maps clause of the Agreement." Google built and markets it precisely for your situation ("bring Google's rich Places content to any map"), it bills as a flat Essentials SKU at 10,000 free calls/month, and a single UI Kit Place Details call returns photos, rating, hours and price with no Enterprise-tier or Photo-endpoint surcharge — which is strictly better economics than the à-la-carte path your CLAUDE.md roadmap plans. Its cost is architectural, not financial: it is a Google-rendered Android widget, not JSON, so it cannot feed OsmAnd's own context menu and it will not render inside Android Auto's restricted templates. Post-March-2025 the $200 universal credit is gone, replaced by per-SKU monthly free allowances of 10,000 (Essentials) / 5,000 (Pro) / 1,000 (Enterprise); at your ~12 searches/day everything you actually want is free, so billing is not your constraint — the ToS and the Android Auto surface are.

## HERE Location Services (HERE Technologies)

HERE's real value to CairoDrive is one thing above all others: it is a full traffic + search + routing stack whose terms do NOT require you to render anything on a HERE basemap. HERE's Base Plan restrictions explicitly permit layering your own and third-party content with HERE content for display, and permit combining HERE results with other content to deliver derived location responses (a route or a search result), provided origins stay distinguishable and attribution is correct. That is the clause that makes HERE legitimately usable on top of OsmAnd's offline OSM vector basemap, where Google's traffic layer is not. Everything else follows from that: the Traffic API v7 flow endpoint returns JSON with real geometry (locationReferencing=shape), so you can annotate the offline route segment-by-segment without any tile pipeline, no MVT decoder, and no second basemap. The catch, and it is a real one that invalidates most guides written before late 2025: the no-credit-card Limited Plan is dead. HERE decommissioned it for new signups on 2025-03-27 and cut off existing users on 2025-08-31. Every new account is now Base Plan, which requires a payment method at onboarding. You are not charged until you exceed a free tier, but the card is on file and overage is billed, not blocked — so this is a "trap" only in the sense that a runaway loop on a moving map costs money instead of erroring. HERE also raised Base Plan and per-transaction pricing ~6% effective 2026-04-01. Against TomTom, which you already have wired up as a raster overlay, HERE is heavily redundant on traffic tiles but strictly better on traffic-as-JSON and adds two things TomTom does not: a Browse endpoint that does category-nearby search (filling the gap left by your Google SearchNearby quota being pinned at 0), and Destination Weather on the same key.

That is route annotation in one request, with no tile pipeline, no MVT decoder, and no second basemap — precisely the shape the architecture asks for.
- traversability=closed on a flow segment, plus the incidents endpoint, gives you road-closure knowledge — the one class of information an offline .obf router structurally cannot have, and the one that most reliably produces a wrong turn.
- The Browse endpoint does category-filtered nearby search with no query string, which fills the exact hole left by your Google SearchNearby quota being pinned at 0. This is additive capability, not a duplicate.
- Autosuggest/Autocomplete billed as ordinary flat transactions rather than Google's per-keystroke session model — structurally cheaper for the most expensive item on the deferred features list.
- A 30-day caching and storage allowance (to the extent necessary to enable or improve an end user's own use) — more permissive than Google's caching rules, and useful for a device with a metered-data saver.
- Destination Weather, Public Transit, EV and routing all sit behind the SAME apiKey and the same account as traffic and search — one credential, one bill, one integration pattern, rather than a separate provider per capability.
- Personal turn-by-turn navigation is NOT among the Base Plan's excluded use cases. The exclusions are Asset Management, Usage-Based Insurance/Telematics, and Optimization — none of which describe a single-driver commute app.

**ToS warnings:**

- THE FREE-WITHOUT-A-CARD ERA IS OVER. The Limited Plan (1,000 requests/day, 5 RPS, no credit card) was decommissioned for new customers on 2025-03-27 and terminated for existing users on 2025-08-31. - HERE raised Base Plan and pay-per-transaction pricing by approximately 6% effective 2026-04-01 for new contracts, renewals and extensions. Any per-1,000 figure quoted from before that date is low.
- Caching is capped at 30 days and only to the extent necessary to enable or improve an end user's use of the service. Building a repository of location assets, or scaling one request to serve multiple end users, is prohibited. Do not accumulate a local Cairo traffic history from the flow endpoint — that is squarely the prohibited use.

- One app ID per application — no sharing across apps, and separate IDs for mobile versus server components.
- Excluded from the Base Plan entirely: Asset Management (locating/tracking/displaying assets, hazard alerts), Usage-Based Insurance and Telematics (post-trip driving analysis), and Optimization (destination ordering / route optimization). ## Mapbox

Mapbox is the best-value traffic-data provider in this comparison set, and the worst-fit search provider. Its one genuinely unique offering for CairoDrive is Map Matching with congestion annotations: you can feed OsmAnd's already-computed offline route polyline into a single REST call and get back per-segment congestion plus traffic-aware durations snapped to Mapbox's road graph — route ANNOTATION on top of the offline route, which is exactly the stated want, and which no other provider in this set does as cleanly. Egypt is explicitly named in Mapbox docs as a country where ETAs use both real-time and typical traffic, and Mapbox's traffic is crowdsourced from ~700M MAU across 45k apps rather than fixed sensors, which tends to favour dense urban arterials like Cairo's. The free tiers are large (100,000 requests/mo on each of Directions, Map Matching, Isochrone; 100,000 Matrix elements; 200,000 static/vector tiles; 750,000 raster tiles) and calling the plain REST endpoints from HttpURLConnection avoids MAU billing entirely — MAU only applies if you link a Mapbox SDK, which CairoDrive must not do. ## Yandex Maps API

Yandex is a genuinely excellent mapping provider — in Russia, the CIS, Türkiye and Kazakhstan. For CairoDrive it is a dead end, and not for one reason but for three independent ones, any of which alone is fatal. (1) COVERAGE: Egypt is not in Yandex's detailed-coverage country list, is not in the Navigator routing country list, has no traffic-jam scoring (that is Russia + Türkiye + Kazakhstan only), and has no panoramas (Russia, Türkiye, Kazakhstan, Armenia, Uzbekistan only). The one 2025 change worth knowing — Tiles API went permanently free on 3 June 2025 — delivers only the raster roadmap basemap CairoDrive does not want, with no traffic layer. ## Geoapify vs LocationIQ (head-to-head; both OSM/Nominatim-derived budget providers)

These two are the same product with different billing metaphors, and for CairoDrive the honest answer is: take Geoapify, skip LocationIQ. Both are thin commercial wrappers over OpenStreetMap (LocationIQ over Nominatim/OSRM, Geoapify over its own OSM+Geonames+WhosOnFirst+OpenAddresses build). In Egypt the extra datasets buy nothing — OpenAddresses has no Egypt corpus — so both collapse to exactly the OSM data OsmAnd already renders offline from the .obf. That kills most of their surface immediately: tiles and static maps duplicate a basemap CairoDrive already draws offline (and cost metered bandwidth to do worse), routing/matrix/directions are explicitly unwanted, and NEITHER PROVIDER HAS TRAFFIC OR INCIDENT DATA — so the one route-annotation capability the project actually wants is absent from both. What survives is search. There Geoapify wins on structure, not volume: its Places API bills 20 POIs per credit (3,000 credits/day ≈ 60,000 POIs/day) and answers exactly the "petrol near me" category query that the Google console currently has quota-blocked at 0/day, and its Place Details API returns OSM opening_hours/phone/website — the free half of the deferred Google Place Details feature. Geoapify's terms permit caching and storage outright. Neither requires their basemap be displayed — the usual killer clause is absent from both — but both require visible attribution on the free plan, and two attribution obligations plus two more API keys baked into BuildConfig is a real cost for a provider that adds nothing Geoapify lacks.

## Azure Maps

Azure Maps is best understood as "TomTom map data + AccuWeather weather data, sold on Azure billing." For CairoDrive that split is decisive. The map/traffic/routing half is TomTom-sourced — i.e. the same upstream data as the TomTom traffic overlay already in the app — so it adds vendor complexity without adding information, and Azure's Product Terms forbid displaying those Results on a non-Microsoft basemap anyway. The weather half is the opposite: AccuWeather-sourced, not redundant with anything already integrated, and (per the March 2025 Product Terms alignment) explicitly carved OUT of the third-party-map restriction alongside geocodes. The standout product is Get Weather Along Route: one GET, up to 60 waypoints each with a lat/lon + ETA-in-minutes + heading, returning per-waypoint precipitation type/intensity (dBZ), wind, wind gusts, lightning count, a 0-4 hazard index, a sun-glare rating computed from the vehicle's heading, and onset notifications for hazards a driver has not reached yet. That maps almost perfectly onto a turn-by-turn app driving an already-computed offline route, and it is ToS-clean on an OSM basemap. Egypt coverage is better than expected across the board (rooftop-accurate address points, real-time traffic flow AND incidents, minute-by-minute precipitation nowcast) with one hard gap: severe weather alerts are NOT available in Egypt, verified in Microsoft's own coverage table. The caution is billing shape — the free allowance is small (5,000 transactions/month per meter), a card is required, and on a converted pay-as-you-go subscription there is no hard stop, only Azure Budget alerts. Gen1 pricing dies 15 Sep 2026 with automatic migration to Gen2 at roughly 9x the per-transaction rate.

|---|---|---|---|---|---|

**Only this provider gives you:**

- Get Weather Along Route - a purpose-built driving-weather endpoint that takes waypoints with per-point ETAs and returns a 0-4 hazard index, precipitation type and dBZ intensity, lightning count, wind gusts, and forward-looking notifications for hazards the driver has not reached yet. Nothing else in the provider set has an equivalent, and it composes with an already-computed offline route instead of requiring online routing.
- Per-waypoint sun-glare rating derived from the vehicle heading you supply (hazard codes SunGlare and SunGlareHigh). A real Cairo hazard on east-west arterials at dawn and dusk, and unique to Azure Maps among the providers under review.
- An explicit ToS carve-out for Weather results alongside geocodes, letting weather data be displayed over a non-Microsoft basemap - the one place Azure Maps' terms actually fit an offline-OSM app rather than fighting it.
- Officially documented rooftop-accurate ('Address points') geocoding in Egypt, the top tier in Microsoft's own coverage table, which is uncommon for North Africa.
- Tile billing at 15 tiles per transaction, roughly an order of magnitude more forgiving than per-tile pricing, and Autocomplete billed at 10 requests per transaction - materially cheaper per keystroke than Google Places Autocomplete's per-session model.
- Snap to Roads returns road names and speed limits for up to 100 points in a single transaction - a cheap way to audit sparse OSM maxspeed coverage in Cairo offline.
- AccuWeather as the weather source, which is genuinely independent of the TomTom/HERE data already in the app, so the weather half is additive rather than duplicative.

**ToS warnings:**

- THE KILLER CLAUSE, and it is the inverse of the usual one. Azure Maps does not require you to display their basemap; it forbids displaying their Results on anyone else's. The Product Terms wording is that the customer may not display any Results, EXCEPT geocodes and/or Azure Maps Weather service results, on any third-party content or geographical map database. OsmAnd's OSM vector basemap is a third-party geographical map database. So: Weather and geocoding are permitted over your map; routing results, traffic flow/incident data and POI results are NOT.
- This makes Azure Maps unusual in a way that happens to suit you - the two things it explicitly permits (Weather, geocodes) are exactly the two things worth taking, and the things it forbids (traffic, routing) are the things you already have from TomTom or do not want.
- Overlaying Azure Maps traffic or weather RASTER TILES on the OSM basemap is the ambiguous middle case. Microsoft publishes an official azure-maps-leaflet plugin and 'Third Party Map Controls' samples, so Render tiles in a non-Microsoft map control are clearly contemplated - but those samples use Azure tiles AS the basemap, not layered over a competitor's. Weather tiles are served by the Render endpoint while the carve-out names the Weather service, so inheritance is unclear. Read the current Product Terms before shipping any tile overlay.
- Attribution is mandatory and dynamic for any Render use. The docs require calling Get Map Attribution and displaying the returned text in the lower right of the map, refreshed on every zoom, pan or style change, because providers vary by region and zoom. Get Map Attribution and Get Copyright are non-billable, so compliance is free - but it is per-interaction work, not a static logo.
- Caching is limited. Results may not be cached or stored to scale across multiple users or to circumvent Azure Maps functionality; caching to reduce latency is permitted. Retention is capped at the validity period in the response headers or 6 months, whichever is shorter. Geocodes are the exception - you may retain continual access to those while the Azure account is active.
- A credit card is mandatory. There is no card-free tier; Azure requires a card for verification even on the free account.
- There is no hard spend stop once you are on pay-as-you-go. The Azure free account carries a spending limit that is on by default and does stop resources when the credit is exhausted - but you must remove that limit and convert to pay-as-you-go within 30 days to keep using the recurring monthly free allowances. After conversion, exceeding the free allowance is silently BILLED. Azure Budgets are alerts, not caps. This is materially weaker than the Google Cloud daily quota cap you already rely on as the control that actually bounds the bill, and it is the single biggest practical argument against leaning on Azure Maps.
- Egypt has no localized 'view' code. The view parameter offers AE, BH, IQ, JO, KW, LB, MA, OM, PS, QA, SA, SY, YE plus Auto and Unified - but no EG. Disputed boundaries relevant to Egypt (notably the Halayeb Triangle) will render per Auto or Unified rather than an Egyptian view. Minor, but worth knowing before showing any Microsoft-rendered geometry to an Egyptian user.

## OpenWeather vs Tomorrow.io (two weather providers, compared)

OpenWeather wins for CairoDrive, and not narrowly. Three structural reasons. (1) Quota shape: OpenWeather's free plan is minute-limited (~60 calls/min) with a large monthly pool, while Tomorrow.io's free plan is hour-limited at ~25 calls/hour — roughly one call every 2.4 minutes. A driving app that refreshes conditions during a trip, or samples N points along a route, blows 25/hour instantly. The daily caps are irrelevant; the hourly cap is the binding constraint and it is disqualifying. (2) Raster tiles: OpenWeather Weather Maps 1.0 is a plain XYZ template (tile.openweathermap.org/map/{layer}/{z}/{x}/{y}.png?appid=), transparent PNG, free, no card. CairoDrive already runs TomTom and HERE traffic raster overlays, so precipitation/clouds/wind/temp become a tile-source config entry, not code. Tomorrow.io's tiles carry a time dimension in the path and are believed paid-gated, so they do not drop into a static template. (3) Dust: OpenWeather's condition-code vocabulary has first-class 7xx atmosphere codes — 731 sand/dust whirls, 751 sand, 761 dust, 771 squalls — returned by the FREE current-weather endpoint, plus a free Air Pollution API with PM10. Tomorrow.io's weatherCode enumeration is, to my knowledge, precipitation-and-cloud only with no sand/dust member, leaving particulateMatter10 as the only dust proxy and burning the same scarce quota. For a car driven through khamsin season in Cairo, that asymmetry decides it. Tomorrow.io's genuine advantage — one POST to /v4/timelines returning many proprietary fields across many timesteps — is real and is the correct way to use it, but it does not outweigh a 25/hour ceiling. Both providers' Road Risk products are winter-driving products (ice, snow accumulation, freezing rain, sub-zero road surface temp); in Cairo those inputs are null year-round, so both are worth zero regardless of price. Neither provider requires its own basemap be displayed — both sell transparent overlays and have no basemap of their own — so the usual killer clause does not fire here for either.

## MapTiler + Stadia Maps (head-to-head)

These two overlap heavily and neither is a traffic or POI provider, so neither displaces what CairoDrive already has (TomTom/HERE raster traffic, Google Places search). MapTiler is a tile-and-geodata vendor: generous request quota (100k/mo free) but its own client README states flatly that "data fetched from MapTiler Cloud API cannot be stored or redistributed in any way" — which collides head-on with an offline-first nav app that caches tiles to sqlite and runs a CD_SEARCH prefix cache. That clause makes almost everything MapTiler sells legally awkward here, and the only thing it offers that OsmAnd cannot already do offline is satellite imagery. Stadia is the more interesting one, for a reason that has nothing to do with maps: it bundles the full Valhalla routing stack free, including map matching (map_match + trace_attributes), which returns per-OSM-edge roadClass, laneCount, surface, speedLimit, wayId and names for a GPS trace. That is an off-device, post-drive measurement tool that plugs straight into the CD_NARROW workstream next to cd-analyze.py, costs nothing at runtime, and touches neither the frame budget nor the battery. Stadia's geocoder also carries Foursquare POIs alongside OSM, which is the only reason its search is more than a second copy of the offline OSM fallback. Verdict: adopt one Stadia feature (map matching, as a laptop-side analysis tool), treat everything else as SKIP or a distant MAYBE, and do not expect either provider to give you traffic.
